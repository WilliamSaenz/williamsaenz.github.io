¿Por qué la Normal es la más usada? Por el Teorema Central del Límite (TCL): la suma o el promedio de muchas variables independientes tiende a una distribución normal, sin importar la distribución original de cada una. Por eso medias muestrales, errores de medición y muchos fenómenos agregados (costos totales, rendimientos promedio) se aproximan bien con una Normal, incluso si el dato individual no lo es. Se usa la Normal cuando: (a) el fenómeno es la suma/promedio de muchos factores, (b) n es grande (n≥30 típicamente), o (c) los datos pasan una prueba de normalidad (Shapiro-Wilk, D'Agostino). Si el dato es un conteo → Poisson/Binomial. Si es un tiempo hasta un evento → Exponencial. Si es siempre positivo y asimétrico (como costos) → evaluar Lognormal.

3 · Estimación y muestreo

3.1 Estimación puntual vs por intervalo

Una estimación puntual da un solo número (ej. la media muestral x̄ estima la media poblacional μ). Un intervalo de confianza (IC) da un rango con un nivel de confianza asociado (ej. 95%), reconociendo la incertidumbre del muestreo.

ConceptoFórmula
Error estándar de la mediaSE = s / √n
IC 95% para la media (n grande)x̄ ± 1.96 · SE
IC para la media (n chico, σ desconocida)x̄ ± t(α/2, n-1) · SE
import scipy.stats as stats
import numpy as np

datos = df['costo_hh'].dropna()
media = datos.mean()
sem = stats.sem(datos)                          # error estandar
ic = stats.t.interval(0.95, len(datos)-1, loc=media, scale=sem)
print(f"Media: {media:.2f} | IC 95%: {ic}")
Teorema Central del Límite (TCL): la distribución de la media muestral se aproxima a una Normal a medida que n crece, sin importar la distribución de la población original. Es la base que justifica usar pruebas basadas en la Normal (t-test, IC) incluso cuando el dato individual no es normal, siempre que n sea razonablemente grande.

4 · Test de hipótesis — el marco general

Todo test de hipótesis (paramétrico o no) sigue la misma lógica. Entenderla es más importante que memorizar cada fórmula.

  1. Planteo H0 y H1. H0 (hipótesis nula) es la afirmación de "no hay efecto/diferencia"; H1 es lo que se quiere demostrar.
  2. Elijo el nivel de significancia α (normalmente 0.05): la probabilidad máxima aceptable de rechazar H0 siendo verdadera.
  3. Calculo el estadístico de prueba (t, F, χ², U, W según el test) a partir de los datos.
  4. Obtengo el p-valor: la probabilidad de observar un resultado igual o más extremo que el mío, si H0 fuera cierta.
  5. Decido: si p-valor < α → rechazo H0 (hay evidencia de efecto/diferencia). Si p-valor ≥ α → no rechazo H0 (no hay evidencia suficiente; esto no prueba que H0 sea verdadera).
ConceptoSignificado
Error tipo I (α)Rechazar H0 cuando en realidad es verdadera (falso positivo)
Error tipo II (β)No rechazar H0 cuando en realidad es falsa (falso negativo)
Potencia (1-β)Probabilidad de detectar un efecto real cuando existe
Test de una colaH1 especifica dirección (ej. "mayor que")
Test de dos colasH1 solo dice "distinto", sin dirección (el más común)
Errores de interpretación frecuentes: un p-valor alto NO prueba que H0 sea cierta, solo que no hay evidencia suficiente para rechazarla. Un resultado "estadísticamente significativo" (p<0.05) no siempre es relevante en la práctica: con muestras muy grandes, diferencias mínimas y sin importancia real pueden dar p-valores muy bajos. Siempre conviene acompañar el p-valor con el tamaño del efecto (ej. diferencia real en $ o en %).

5.4 Regresión lineal simple

Modela una variable numérica y en función de una variable x: y = β₀ + β₁x + ε.

ElementoInterpretación
β₀ (intercepto)Valor esperado de y cuando x = 0
β₁ (pendiente)Cuánto cambia y por cada unidad que aumenta x
R²% de la variabilidad de y explicada por x (0 a 1)
R² ajustadoR² corregido por la cantidad de variables usadas (ver nota abajo)
p-valor de β₁Si β₁ es significativamente distinto de 0 (relación real)
R² ajustado — por qué importa: el R² normal siempre sube (o queda igual) al agregar más variables predictoras, aunque esas variables no aporten nada real — por eso no sirve para comparar modelos con distinta cantidad de variables. El R² ajustado penaliza por la cantidad de predictores (k) y el tamaño de muestra (n):
R²_ajustado = 1 - (1-R²)·(n-1)/(n-k-1)
Si al agregar una variable el R² ajustado baja, esa variable no compensa la complejidad que agrega — es la señal de que no conviene incluirla. En statsmodels, modelo.summary() ya lo muestra como Adj. R-squared junto al R² normal, sin necesidad de calcularlo a mano.
import statsmodels.api as sm

X = df['hh_invertidas']
y = df['metros_ejecutados']
X = sm.add_constant(X)          # agrega el intercepto

modelo = sm.OLS(y, X).fit()
print(modelo.summary())         # tabla completa: coef, std err, t, p, R2, IC

# Prediccion
pred = modelo.predict([1, 500])  # [constante, hh_invertidas=500]

5.5 Regresión lineal múltiple

Extiende el modelo a varias variables predictoras: y = β₀ + β₁x₁ + β₂x₂ + ... + βₙxₙ + ε. Es el análogo estadístico de un APU (análisis de precios unitarios): cada β indica el aporte marginal de esa variable al costo/avance, controlando por las demás.

Supuesto adicionalCómo verificarlo
No multicolinealidadVIF (Variance Inflation Factor) < 5-10
Homocedasticidad de residuosstatsmodels.stats.diagnostic.het_breuschpagan
Normalidad de residuosQQ-plot + Shapiro-Wilk sobre modelo.resid
En regresión múltiple, conviene mirar siempre el R² ajustado (no el R² normal) para decidir si conviene agregar una variable más. Con muchas variables candidatas (ej. metros, tableros, HH, cantidad de RFI, días de atraso documental), comparar el R² ajustado entre versiones del modelo evita "inflar" el ajuste artificialmente agregando predictores irrelevantes.
import statsmodels.api as sm
from statsmodels.stats.outliers_influence import variance_inflation_factor
import statsmodels.stats.diagnostic as dg

X = df[['metros_caneria', 'cant_tableros', 'hh_planificadas']]
X = sm.add_constant(X)
y = df['costo_final']

modelo = sm.OLS(y, X).fit()
print(modelo.summary())

# Multicolinealidad (VIF por variable)
vif = pd.DataFrame()
vif['variable'] = X.columns
vif['VIF'] = [variance_inflation_factor(X.values, i) for i in range(X.shape[1])]

# Homocedasticidad de residuos (Breusch-Pagan)
bp_stat, bp_p, _, _ = dg.het_breuschpagan(modelo.resid, modelo.model.exog)
print('p-valor Breusch-Pagan:', bp_p)   # si p < 0.05, hay heterocedasticidad
Caso práctico — estimar el costo final de un frente MEP

Regresión múltiple con costo_final ~ metros_caneria + cant_tableros + hh_planificadas. El coeficiente de cant_tableros dice cuánto sube el costo final por cada tablero adicional, manteniendo constantes las otras variables — un dato mucho más útil para presupuestar que un promedio simple.

chi2, p, dof, esperado = stats.chi2_contingency(tabla)
Caso práctico — ¿cambió el rendimiento tras una capacitación?

Rendimiento (m/HH) de una cuadrilla eléctrica antes y después de capacitarla. 1) Graficar y correr Shapiro-Wilk. 2) Si hay normalidad → t pareada. 3) Si no → Wilcoxon signed-rank. 4) Reportar siempre el p-valor y el tamaño de muestra.

Regla de oro: primero se grafican los datos, después se corre la prueba de normalidad, y recién ahí se elige el test. Nunca forzar una prueba paramétrica sin revisar sus supuestos — y siempre reportar el tamaño del efecto, no solo el p-valor.

Overfitting y underfitting — la tensión central de todo modelo

ProblemaQué pasaCómo se detectaCómo se corrige
Overfitting (sobreajuste)El modelo memoriza el ruido del set de entrenamiento y generaliza mal a datos nuevosError muy bajo en train, alto en testMás datos, regularización, simplificar el modelo, validación cruzada
Underfitting (subajuste)El modelo es demasiado simple para capturar el patrón realError alto tanto en train como en testModelo más complejo, agregar variables relevantes, menos regularización
La forma correcta de detectar ambos: separar siempre en train/test (o usar validación cruzada) y comparar el error en ambos conjuntos. Si el modelo es "demasiado bueno" en train pero falla en test, es overfitting — señal de que aprendió el dato de memoria, no el patrón.

Programación orientada a objetos (lo mínimo útil)

No hace falta ser experto en POO, pero reconocerla ayuda a leer librerías (un DataFrame de pandas es un objeto con métodos). Una clase agrupa datos (atributos) y comportamientos (métodos); un objeto es una instancia concreta de esa clase.

class Obra:
    def __init__(self, nombre, presupuesto):
        self.nombre = nombre
        self.presupuesto = presupuesto
        self.costo_real = 0

    def registrar_costo(self, monto):
        self.costo_real += monto

    def desvio_pct(self):
        return (self.costo_real - self.presupuesto) / self.presupuesto

obra1 = Obra("Torres del Sol", 10_500_000)
obra1.registrar_costo(3_200_000)
print(obra1.desvio_pct())

class ObraMEP(Obra):

        super().__init__(nombre, presupuesto)

=BUSCARX(valor_buscado, matriz_buscada, matriz_devuelta, [si_no_hay], [modo_coincidencia], [modo_busqueda])

// Ejemplo: traer el nombre del proveedor a partir del ID
=BUSCARX(A2, Proveedores!A:A, Proveedores!B:B, "No encontrado")

// Ejemplo: traer varias columnas a la vez (matriz devuelta = rango, no una sola columna)
=BUSCARX(A2, Proveedores!A:A, Proveedores!B:D)
Ventaja vs BUSCARVDetalle
Busca en cualquier direcciónNo necesita que la columna buscada esté a la izquierda
Valor por defecto incluidoEvita anidar SI.ERROR
Devuelve varias columnasUn solo BUSCARX puede traer un rango completo
Coincidencia aproximada configurableÚtil para tablas de rangos (ej. tramos de tarifa)
Si la versión de Excel disponible no tiene BUSCARX (empresas con licencias antiguas), el equivalente es =INDICE(matriz_devuelta, COINCIDIR(valor_buscado, matriz_buscada, 0)) — funciona igual y es más portable entre versiones.

2 · Tablas dinámicas — paso a paso

  1. Convertir el rango de datos en Tabla (Ctrl+T) para que se actualice automáticamente al crecer.
  2. Insertar → Tabla dinámica → elegir la Tabla como origen.
  3. Arrastrar campos: Filas (categorías a agrupar, ej. Obra), Columnas (ej. Mes), Valores (ej. Suma de Costo), Filtros (ej. Proveedor).
  4. Clic derecho en un valor → Configuración de campo de valor → elegir Suma/Promedio/Cuenta/% del total.
  5. Agregar Segmentadores (Analizar → Insertar segmentador) para filtrar de forma visual.
  6. Agrupar fechas: clic derecho sobre una fecha → Agrupar → por Mes/Trimestre/Año.
Caso práctico — costo por obra y por mes

Filas: Obra. Columnas: Mes. Valores: Suma de costo_total. Filtro: Proveedor. Resultado: una matriz Obra × Mes lista para detectar la obra con mayor desvío, sin escribir una sola fórmula.

7 · Ejercicio práctico — BUSCARX con coincidencia aproximada (tablas por rango)

Además de la búsqueda exacta, BUSCARX resuelve muy bien las tablas de rango (tramos de tarifa, categorías por antigüedad, escalas de comisión). El truco: la matriz buscada debe estar ordenada ascendente y el modo de coincidencia debe ser "menor o igual".

DesdeHastaCategoría
30.00032.000Nivel 1
32.00036.000Nivel 2
36.00040.000Nivel 3
40.00044.000Nivel 4
// Buscar la categoria de un valor contra una tabla de rangos "Desde"
=BUSCARX(valor, Tabla[Desde], Tabla[Categoria], "Fuera de rango", -1)
// El ultimo argumento -1 = "coincidencia exacta o el valor menor mas cercano"
// Equivalente clasico con BUSCARV (coincidencia aproximada = VERDADERO):
=BUSCARV(valor, Tabla_rangos, 3, VERDADERO)
Práctica: armar una tabla con columnas Desde/Hasta que se autocompleten con =Hasta_anterior y =Desde+intervalo (así no hay huecos ni superposición entre tramos), y probar el cruce con BUSCARX y con BUSCARV para confirmar que ambos dan el mismo resultado. Es exactamente el mismo patrón que se usaría para categorizar OC por monto o personal por antigüedad.
Caso práctico integrador — reporte semanal 100% automatizado en Excel

Power Query consolida los partes diarios de la carpeta compartida cada vez que se abre el archivo → Power Pivot los relaciona con la tabla de tarifas y Calendario, y calcula %Avance, Desvío de Costo y OC Pendientes con DAX → una tabla dinámica arma el resumen ejecutivo por obra y disciplina → una macro aplica el formato final, colorea los semáforos y exporta a PDF con un clic.

3 · Modelado de datos — cómo se relacionan las tablas

Esquema estrella

Una tabla de hechos central (los eventos que se miden: costos, avance, compras) rodeada de tablas de dimensión (el contexto: Obra, Disciplina, Proveedor, Fecha). Las dimensiones se conectan a los hechos con relaciones 1 a muchos.

Cómo crear una relación

  1. Vista de modelo (ícono lateral) → arrastrar el campo clave de la dimensión (ej. Dim_Obra[id_obra]) hacia el campo equivalente en la tabla de hechos.
  2. Power BI detecta la cardinalidad (uno a muchos, muchos a muchos) y la dirección del filtro automáticamente — revisarla igual.
  3. Doble clic en la relación para editar: cardinalidad, dirección de filtro cruzado (única vs ambas), activa/inactiva.
ConceptoQué significa
Cardinalidad 1:NUn valor en la dimensión corresponde a muchas filas en los hechos (lo normal y recomendado)
Dirección únicaEl filtro va de la dimensión hacia los hechos (mejor rendimiento, usar por defecto)
Dirección ambas (bidireccional)El filtro va en los dos sentidos; usar solo si es realmente necesario (puede generar ambigüedad)
Tabla CalendarioTabla de fechas dedicada, relacionada 1:N con cada tabla de hechos que tenga una fecha; imprescindible para medidas de tiempo (YTD, mismo mes año anterior)
// Crear una tabla Calendario con DAX (Modelado -> Nueva tabla)
Calendario =
ADDCOLUMNS(
    CALENDAR(DATE(2025,1,1), DATE(2026,12,31)),
    "Año", YEAR([Date]),
    "Mes", FORMAT([Date], "MMMM"),
    "NroMes", MONTH([Date]),
    "Trimestre", "T" & FORMAT([Date], "Q")

4 · DAX — columnas calculadas vs medidas

AspectoColumna calculadaMedida
¿Cuándo se calcula?Al cargar los datos (una vez, fila por fila)En el momento de la consulta (según el filtro activo)
¿Responde a filtros del reporte?NoSí — esa es su ventaja
Uso típicoClasificaciones fijas, claves concatenadasKPIs: sumas, promedios, %, rankings

Contexto: la idea más importante de DAX

Contexto de fila: al calcular una columna, DAX "sabe" en qué fila está. Contexto de filtro: al calcular una medida, DAX aplica automáticamente los filtros activos (segmentadores, filas de una tabla, filtros de página). CALCULATE() es la función que modifica el contexto de filtro — es la más importante y la más difícil de dominar en DAX.

SAP — cómo pensar el sistema antes de operarlo

SAP organiza todo alrededor de módulos (áreas funcionales) que comparten una base de datos única. Para control de proyectos en infraestructura, los tres de uso más frecuente son PS (Project System — estructura y presupuesto), MM (Materials Management — compras y stock) y CO (Controlling — costos por centro de costo). Cada módulo tiene sus propias transacciones (T-codes) y tablas de base de datos.

  3. Redes y actividades — el detalle de tareas dentro de un WBS, a veces vinculadas al cronograma externo (Primavera).

Curva S — avance planificado (PV), avance real (EV) y costo real (AC), acumulado mensual

La Curva S es la herramienta central de control de un proyecto: compara en un mismo gráfico cuánto deberías haber avanzado (PV), cuánto realmente avanzaste convertido en $ (EV) y cuánto realmente gastaste (AC). Las tres curvas nacen en 0% y terminan en 100% del presupuesto — la forma de "S" refleja que el proyecto arranca lento (movilización, ingeniería), acelera en la ejecución principal y vuelve a desacelerar al cierre (pruebas, punch list, entrega).

Las filas marcadas con RUTA CRÍTICA en las tablas de abajo son las que, según la lógica de este cronograma, tienen holgura cero: cualquier día de atraso ahí atrasa la fecha fin del proyecto completo. Cómo leer este cronograma como Analista de Planificación y Control

Se observan 3 patrones típicos de un EPC lineal: (1) los Hitos (H01-H20) son la columna vertebral que se reporta al cliente — cada hito tiene fecha comprometida y real/proyectada, ideal para el semáforo ejecutivo. (2) La secuencia de la Línea Regular (A1000-A1140) es un tren de actividades encadenadas con solape (apertura de pista → desfile → curvado → soldadura → revestimiento → zanjeo → bajada → tapada) — es el patrón clásico de "spread" de tendido de ductos, cada actividad sigue a la anterior con un lag corto. (3) Las provisiones (códigos que dicen "Provisión...") suelen tener 0 días de duración porque son hitos de fecha de entrega, no tareas con avance — pero son las que más riesgo de atraso le meten al cronograma aguas abajo si el proveedor se demora.

Caso integral: proyecto MEP de punta a punta

Esta pestaña simula situaciones reales que enfrenta un Analista/Administrativo de Obra: no son solo preguntas técnicas de una disciplina, sino problemas cruzados entre planificación, costos, compras, calidad y personas — el perfil "pulpo" que exige el rol.

Eléctrica — avance y materiales críticos

Situación: faltan 6 semanas para la fecha comprometida de energización y el % de avance eléctrico viene 12 puntos por debajo del plan.

Pregunta: ¿vamos a poder energizar el tablero principal a tiempo? ¿es un problema de mano de obra o de materiales?

Flujo de análisis: Python consolida partes diarios (metros de cableado tendido por día) → SQL/ERP trae el estado de las OC de cables y tableros con su lead time → Power BI calcula % Avance Eléctrico y un semáforo de "Riesgo Material Crítico" cruzando fecha de necesidad (del cronograma) vs. fecha de entrega comprometida (de la OC) → si el material está a tiempo pero el avance no sube, el problema es de dotación/rendimiento: usar t pareada o Wilcoxon para comparar el rendimiento de las cuadrillas actuales contra el rendimiento planificado.

Solución típica: si el cuello de botella es material → escalar a compras con el lead time exacto y evaluar flete expreso. Si es de cuadrilla → reforzar con HH extra en el frente crítico y replanificar la secuencia de tableros por prioridad de energización.

Estructura — hormigonado y ruta crítica

Situación: el frente de estructura, que está en la ruta crítica del proyecto, muestra un SPI de 0,85 hace 3 semanas consecutivas.

Pregunta: ¿el atraso estructural va a mover la fecha de entrega general del proyecto?

Flujo de análisis: cruzar PV acumulado (Primavera/MS Project, en m³ de hormigón) con EV real (partes diarios) → calcular SPI de estructura por separado del SPI general del proyecto (un SPI global "aceptable" puede esconder un frente crítico muy atrasado) → analizar dispersión del rendimiento (m³/día) por cuadrilla para detectar si el problema es puntual (una cuadrilla) o generalizado (clima, provisión de hormigón elaborado).

Solución típica: si está en ruta crítica, cualquier día de atraso acá mueve la fecha fin del proyecto 1 a 1 — se prioriza sobre cualquier otro frente no crítico: turnos adicionales, doble cuadrilla, o adelantar actividades sucesoras que no dependan 100% de esta para "amortiguar" el atraso.

Sanitaria / Piping — pruebas hidráulicas y trazabilidad

Situación: el cliente pide un reporte de trazabilidad de cañerías instaladas, probadas y aprobadas antes de una auditoría.

Pregunta: ¿cuántos metros de cañería están instalados, probados y aprobados por sistema (agua, cloacal, gas)?

Flujo de análisis: unificar partes diarios de piping (requiere más limpieza de texto libre que otras disciplinas) → construir un embudo instalado → probado → aprobado por sistema → usar Chi-cuadrado para ver si el tipo de sistema está asociado a un tipo particular de no conformidad (ej. las juntas de gas fallan más que las de agua) → dashboard con el embudo y el detalle de NCR abiertas por sistema.

Solución típica: si un sistema concentra NCR, foco de auditoría e inspección reforzada ahí antes de que llegue el cliente, no distribuir el esfuerzo por igual en los 3 sistemas.

HVAC / Mecánica — coordinación de interferencias

Situación: en obra aparece una interferencia entre un ducto de HVAC y una viga estructural que no estaba prevista en el modelo.

Pregunta: ¿cómo se resuelve sin frenar 2 frentes a la vez, y quién aprueba el cambio?

Flujo de análisis: registrar la interferencia como RFI dirigido a ingeniería (ver pestaña 15 · Gestión Documental) → mientras se espera respuesta, replanificar la secuencia local para no dejar sin frente a la cuadrilla de HVAC (adelantar otra zona) → una vez resuelto, el ajuste se documenta como redline sobre el plano IFC vigente.

Solución típica: escalar el RFI con fecha límite de respuesta clara y cuantificar el impacto en días si no se resuelve a tiempo — eso convierte una duda técnica en una prioridad de gestión.

Administrativo de Obra — orden de compra crítica demorada

Situación: una OC de un material de largo lead time (ej. válvulas actuadas) lleva 10 días de atraso respecto a la fecha de entrega comprometida por el proveedor.

Pregunta: ¿qué actividades del cronograma se ven afectadas y con cuánta anticipación hay que avisar?

Flujo de análisis: cruzar la fecha de necesidad de la actividad sucesora (del cronograma) contra la nueva fecha estimada de entrega → calcular el atraso proyectado en la actividad dependiente → si esa actividad tiene poca holgura (float bajo en Primavera), el atraso de compra se traslada directo al proyecto.

Solución típica: armar el email de escalamiento (ver pestaña 10 · Plantillas) con el impacto cuantificado en días y $, y proponer 2-3 alternativas (flete expreso, proveedor alternativo, resecuenciar actividades no críticas) para que quien decide tenga opciones, no solo el problema.

Administrativo de Obra — ausentismo y baja productividad de una cuadrilla

Situación: RRHH reporta que una cuadrilla tiene 18% de ausentismo en las últimas 2 semanas y control de obra ve que su rendimiento (m²/HH) cayó.

Pregunta: ¿el ausentismo está explicando la caída de rendimiento, o son dos problemas distintos?

Flujo de análisis: cruzar el % de ausentismo semanal con el rendimiento real de la cuadrilla (correlación de Pearson/Spearman según la forma de los datos) → si hay correlación fuerte, el problema es de dotación efectiva; si no, revisar otras causas (materiales, clima, capacitación).

Solución típica: si el ausentismo explica la caída, coordinar con RRHH un refuerzo temporal de dotación; si no, involucrar al capataz/jefe de frente para entender causas operativas antes de tomar una decisión de personal.

El rol del Data Analyst — antes de las herramientas

Un Data Analyst recolecta, limpia, analiza y comunica datos para responder preguntas de negocio concretas. La herramienta (Excel, SQL, Python, Power BI) es secundaria: lo que define el rol es el workflow.

Workflow del Data Analyst (paso a paso)

  1. Entender la pregunta de negocio — qué decisión se quiere tomar con esto.
  2. Identificar y recolectar las fuentes de datos necesarias.
  3. Limpiar y transformar — nulos, duplicados, tipos de dato, formatos.
  4. Modelar — relacionar tablas, definir hechos y dimensiones.
  5. Analizar — resumir, comparar, filtrar, detectar desvíos.
  6. Comunicar — dashboard, reporte o email ejecutivo con hallazgos accionables.

Ciclo de vida del dato

Generación (se crea el dato: un parte diario, una OC) → Recolección (se extrae de la fuente) → Almacenamiento (Excel, base SQL, Data Warehouse) → Procesamiento (limpieza, transformación) → Análisis (KPIs, modelos) → Visualización/uso (dashboard, decisión) → Archivo o descarte.

Datos vs. información: un dato aislado ("6.500") no dice nada; se convierte en información cuando tiene contexto ("$6.500 de sobrecosto en Obra Torre del Sol, semana 20"). El trabajo del analista es justamente ese: agregar contexto y estructura al dato crudo.

Normalización — por qué separar tablas en vez de usar una sola planilla gigante

Normalizar es organizar los datos para que cada hecho viva en un solo lugar, evitando redundancia e inconsistencias (ej. el nombre de un proveedor escrito de 3 formas distintas).

  1. 1FN: cada celda tiene un solo valor (nada de "Juan, Pedro" en una misma celda).
  2. 2FN: todo campo depende de la clave primaria completa.
  3. 3FN: ningún campo depende de otro campo que no sea la clave (ej. no repetir "nombre de obra" en la tabla de costos si ya existe en la tabla Obras).
En la práctica de Power BI/Power Pivot esto es exactamente el esquema estrella (ver pestaña 06 · Power BI): una tabla de hechos (normalizada) y dimensiones alrededor, en vez de una única tabla plana con todo repetido.

Business Intelligence, KPIs y métricas

¿Qué es BI?

Business Intelligence es el proceso de transformar datos dispersos en información que soporta decisiones: fuentes → ETL → modelo de datos → visualización → decisión. No es solo "hacer un dashboard": incluye definir qué preguntas responder y quién es el dueño de cada dato.

KPI vs. métrica

MétricaKPI
Describe un hecho (ej. "cantidad de OC emitidas")Está ligado a un objetivo de negocio, con meta y umbral (ej. "OTIF ≥ 90%")
No necesariamente accionable por sí solaDebe habilitar una decisión concreta

Gestión documental en ingeniería civil — el ciclo de vida de un documento

Todo plano, especificación o procedimiento en un proyecto de obra pasa por el mismo ciclo, sin importar la disciplina. Dominarlo es tan importante como dominar Excel o SQL para quienes trabajan en administración de obra o en planificación y control.

  1. Elaboración — el documento se crea (revisión alfabética, "trabajo en curso").
  2. Revisión interna — control de calidad propio antes de emitirlo afuera.
  3. Emisión para revisión/aprobación (IFR / IFA) — se manda al cliente o a otra disciplina para comentarios.
  4. Comentarios y re-emisión — se incorporan observaciones, sube la revisión (A→B→C...).
  5. Aprobación / emisión para construcción (AFC / IFC) — pasa a numeración (Rev. 0) y ya es válido para ejecutar en obra.
  6. Cambios en campo — se marcan a mano sobre el plano IFC (redline).
  7. Documentación As-Built — se traspasan los redlines a un plano limpio que refleja cómo quedó realmente construido.
  8. Conforme a Obra (CAO) — el paquete final As-Built, aprobado por el cliente, que cierra el proyecto documentalmente.
Regla de oro: nunca se construye con un plano en revisión alfabética (A, B, C...) — esos son borradores en revisión. Solo se construye con un documento en revisión numérica y estado IFC/AFC ("Bueno para construcción"). Si en el sitio hay dudas de qué revisión es la vigente, siempre se verifica contra el MDR (Registro Maestro de Documentos), nunca contra la copia que alguien tiene guardada en su PC.

Revisiones — qué significa cada letra y cada número

La convención más usada en EPC/construcción (aunque cada proyecto la fija en su Plan de Gestión Documental) es: revisiones alfabéticas mientras el documento está en desarrollo/revisión, y revisiones numéricas una vez que el documento ya fue emitido oficialmente (aprobado o para construcción).

RevisiónSignificado práctico
Rev. A (o P1)Primera versión emitida para revisión interna o del cliente. Es un borrador — no sirve para construir.
Rev. B (o P2)Segunda versión, incorpora comentarios de la Rev. A. Sigue siendo borrador/en revisión.
Rev. C, D, E...Sucesivas rondas de comentarios hasta que el documento queda sin observaciones ("comentarios cerrados").
Rev. 0Primera emisión oficial/aprobada del documento — ya es válida para construir (si el estado es IFC) o para uso formal.
Rev. 1, 2, 3...Revisiones oficiales posteriores a la Rev. 0, cada una por un cambio formal aprobado (no por comentarios de borrador).
Ojo con la confusión más común: pasar de Rev. C directo a Rev. 0 (no a "Rev. D") es correcto — el salto de letra a número marca justamente el paso de "borrador" a "documento oficial". Ver una Rev. 0 después de una Rev. C no es un error de numeración.

Cómo se arma una certificación de obra

La certificación nace del acumulado de partes diarios, informes semanales y el informe mensual. La cadena, en términos simples:

  1. Parte diario — registra lo ejecutado ese día: actividad, unidad, cantidad, zona, personal y equipos presentes, novedades. Es el dato crudo del sistema.
  2. Informe semanal — Planificación consolida los partes diarios de la semana por actividad (código WBS), calcula avance físico plan vs. real, desvíos, Curva S y proyección a corto plazo.
  3. Informe mensual — agrega el acumulado del mes, replantea el forecast de fin de obra y documenta desvíos relevantes con sus causas.
  4. Certificación — Planificación traduce el % de avance físico ejecutado (por ítem de WBS/rubro) a unidades certificables según el contrato, aplicando el precio unitario (APU) correspondiente a cada ítem. Ese cálculo (avance físico verificado × precio contractual) es lo que se presenta al cliente para su aprobación, y una vez aprobado, habilita la factura/cobro del período.
El orden y la trazabilidad de la documentación de campo son críticos para este flujo: un parte diario mal cargado o cargado tarde puede atrasar un cobro completo. Es exactamente el tipo de proceso que sostiene un rol de administración/planificación y control: mantener trackers y documentación de respaldo actualizados para certificaciones, facturación, auditorías y reportes.

Costeo por Actividad (IDT) y Valor Ganado — el flujo completo

El objetivo: saber, por cada actividad, cuánto se está gastando en cada tipo de recurso — mano de obra, equipos, materiales, servicios/logística, hospedaje — todo convertido a pesos y asignado a un centro de costo (IDT: el código de esa actividad).

  1. Captura de datos — partes diarios de producción, hojas de horas/RRHH, partes de equipos, facturas/contratos, órdenes de compra, reportes de ingeniería, checklists/ensayos, registro de viáticos/hotel.
  2. Cálculo de costo por recurso — cada tipo de recurso tiene su propia forma de medirse y su propia tarifa.
  3. Asignación a Actividad (IDT) — cada recurso se asigna al centro de costo correspondiente según el parte diario.
  4. Valor Ganado (EVM) — PV, EV, AC por actividad.
  5. Análisis y Control — CV, CPI, SPI, EAC: se compara avance físico vs. costo real y proyectado.
  6. Reporte Ejecutivo — costo acumulado, avance físico %, variaciones y proyección a término, por IDT y por área.

¿Es lo mismo que un Análisis de Precio Unitario (APU)?

Son primos hermanos, no la misma cosa.

ConceptoCuándo se hacePara qué sirve
APU (Análisis de Precio Unitario)Antes de ejecutar, en la etapa de presupuestoDescompone el costo de una unidad de obra (ej. "1 m de soldadura") en sus insumos — mano de obra, equipo, materiales — con rendimientos estimados, para llegar a un precio unitario que se usa para cotizar o certificar
Costeo por Actividad / IDTDurante la ejecución, en control de obraToma el consumo real de recursos (horas reales, materiales reales) y lo valoriza con tarifas reales, para saber qué costó de verdad esa actividad y compararlo contra lo que el APU había estimado
El APU da el costo unitario planificado antes de arrancar; el costeo por actividad da el costo real durante la ejecución. Cruzando los dos se obtiene el CPI de esa actividad puntual — si el consumo real de HH o de equipo superó el rendimiento que asumió el APU, ahí es exactamente donde se está perdiendo dinero.

  • Compras y Contratos — materiales, equipos, servicios

  • Logística y Servicios Generales — transporte, oficinas, generadores, combustible

Interpretación rápida del ejemplo

CPI < 1 → se está gastando más de lo ganado. SPI < 1 → hay atraso en el plazo. EAC > BAC → el proyecto se estima que terminará costando más de lo presupuestado. En este ejemplo, A07 está adelantada en avance (90% vs. lo esperado) pero con sobrecosto real — exactamente el tipo de cruce que un buen control de costos tiene que detectar a tiempo, no al cierre del proyecto.

Flujo de información y buenas prácticas

Parte diario/reportes → Consolidación de datos → Cálculo de costos por recurso → Asignación a IDT → Cálculo EVM → Reporte y análisis

  • Registrar datos todos los días — no dejar que se acumulen.
  • Unificar tarifas y centros de costo entre todas las áreas.
  • Revisar y validar mediciones antes de cargarlas.
  • Conciliar costos reales con contabilidad periódicamente.
  • Actualizar el EVM semanalmente, no solo al cierre de mes.
  • Identificar desviaciones y tomar acciones — el reporte sirve si genera una decisión, no solo un número.

¿Con qué software se hace el costeo por actividad?

Excel — la base que casi cualquier obra tiene disponible

Metodología: Power Query para consolidar automáticamente los partes diarios de cada área en una sola tabla; tablas dinámicas para agrupar el costo por IDT y por área; BUSCARX/XLOOKUP para traer la tarifa de cada recurso desde una tabla maestra; fórmulas para armar PV/EV/AC/CPI/SPI.

  • Power Query — importa y limpia los partes diarios de cada área automáticamente
  • BUSCARX / BUSCARV — trae la tarifa de cada recurso desde la tabla maestra
  • SUMAR.SI.CONJUNTO — consolida el costo por IDT y por área
  • Tablas dinámicas + gráficos — arma el reporte ejecutivo y la Curva S

Conviene para obras chicas/medianas, equipos sin acceso a BI, o cuando el volumen de partes diarios es manejable. Se vuelve lento y frágil si crece mucho el volumen o si varias personas editan el mismo archivo a la vez.

Power BI — cuando el dashboard tiene que llegar a gerencia

Metodología: Power Query (mismo motor que Excel) para el ETL, conectando a la carpeta de partes diarios o a una base SQL; modelo de datos con tabla de hechos (partes diarios) relacionada con dimensiones (tarifas, actividades/IDT, áreas, calendario); medidas DAX para calcular PV, EV, AC, CPI y SPI dinámicamente; segmentadores para filtrar por actividad, área o semana.

  • Power Query — mismo ETL que en Excel, alimentando el modelo de Power BI
  • Modelo relacional (star schema) — hechos + dimensiones para que las medidas calculen rápido
  • DAX — ej. EV = SUMX(Partes, Partes[%Avance] * Partes[PV])
  • Segmentadores — filtran el dashboard sin tocar la fuente de datos

Conviene cuando los datos ya están consolidados (de Excel o SQL) y gerencia necesita navegar el dashboard sin abrir ningún Excel.

Python — cuando el proceso se repite y conviene automatizarlo

Metodología: pandas lee y consolida los partes diarios (Excel/CSV) de cada área en un solo DataFrame; se cruza (merge) con una tabla de tarifas; groupby('IDT') consolida el costo por actividad; se calculan columnas de PV/EV/AC/CPI/SPI directamente; se grafica la Curva S automáticamente.

  • pandas — carga, limpieza y consolidación de los partes diarios
  • openpyxl — leer y escribir archivos Excel directamente
  • numpy — cálculos numéricos (CPI, SPI, EAC)
  • matplotlib / plotly — Curva S y gráficos del reporte
  • sqlalchemy — si el origen de datos es una base SQL en vez de archivos sueltos

La ventaja real: se puede automatizar con un script que corra solo todas las mañanas y deje el reporte listo — es la diferencia entre armar el reporte y que el reporte se arme solo. Conviene cuando el proceso se repite semana a semana.

SQL — la fuente única de verdad cuando el volumen crece

Metodología: una base de datos con tablas partes_diarios, tarifas, actividades (IDT) y areas; los partes diarios se cargan como filas; con JOIN se cruza cada recurso consumido con su tarifa; con GROUP BY se consolida el costo por IDT y por área; se puede crear una VIEW que ya calcule PV/EV/AC, para que Power BI o Python solo la consulten.

SELECT idt, SUM(cantidad*tarifa) AS costo_real
FROM partes_diarios p
JOIN tarifas t ON p.recurso_id = t.recurso_id
GROUP BY idt;

Conviene cuando el volumen de datos crece (muchos partes diarios, muchos meses de histórico) y hace falta que Excel, Power BI y Python trabajen todos sobre la misma fuente de verdad, sin duplicar planillas.

Cómo se conectan entre sí: Partes diarios (Excel) → SQL como base de datos central (una sola fuente de verdad) → Python para automatizar la carga y los cálculos pesados → Power BI como capa de visualización interactiva para gerencia → Excel para reportes puntuales o para quien necesite el detalle fila por fila. No compiten entre sí — cada uno resuelve una parte distinta de la cadena.

Trackers — qué son y por qué se llevan aparte del cronograma

Un tracker es una planilla viva — no un reporte que se cierra y se archiva — que sigue el estado de un conjunto definido de elementos (documentos, actividades, restricciones) a lo largo del tiempo, con un responsable y un estado claro para cada uno. La regla de oro: un tracker sin fecha de última actualización y sin responsable por fila no sirve, es solo una lista.

A continuación, los tres trackers más pedidos en control de obra — documentación, avance físico y restricciones — con ejemplos construidos sobre el mismo cronograma de referencia de la pestaña 08, para que los códigos de actividad sean consistentes en toda la guía.

Buenas prácticas para cualquier tracker

  • Una sola fuente de verdad — si el mismo dato vive en dos trackers distintos, van a terminar desincronizados.
  • Responsable por fila, no por tracker entero — "RRHH" no es un responsable; una persona con nombre y apellido sí lo es.
  • Fecha de última actualización visible — un tracker sin fecha reciente es peor que no tener tracker, porque genera falsa confianza.
  • Semáforo de estado simple (verde/amarillo/rojo) — que se entienda de un vistazo sin tener que leer cada fila.
  • Revisión en reunión semanal — el tracker sirve si genera una decisión o una escalación, no si solo se actualiza y se archiva.
